# VIndex V1 Benchmarks & Performance Analysis

> [!NOTE]
> **Architecture Evolution**: Sections 1–4 document the baseline benchmark results for the **V1 Pipeline with Pebble WAL enabled** (transient WAL `'w'` prefix in Pebble DB, managed by `WalReaper`). Sections 5–7 document the **Zero-WAL Direct Commit Pipeline**, which eliminates write-ahead logging in favor of direct chunk indexing and managed tile caching.

---

## 1. Test Environment & Hardware Context

All benchmarks were conducted under a standardized local dual-process topology:

- **Host Operating System**: Linux
- **Storage Subsystem**: Local high-performance NVMe SSD
- **Dual-Process Topology**:
  - `vindex-hammer`: Tessera POSIX Input Log sequencer and Checkpoint Drip Proxy listening at `http://127.0.0.1:8085`.
  - `vindexd`: Verifiable Index Daemon (Ingestion, KV Indexer, Output Log Publisher, and HTTP Serving API) listening at `http://127.0.0.1:8088`.
- **Communication Channel**: Local loopback HTTP (`:8085` -> `:8088`).

## 5. Zero-WAL Ingestion Architecture Performance

The Zero-WAL direct-commit ingestion architecture eliminates the intermediate Pebble Write-Ahead Log (`'w'`), replacing it with a 3-stage pipelined direct-commit model. Raw entry bundles are pre-cached in `ManagedTileCache`, leaf mapping executes across parallel workers (`runtime.GOMAXPROCS(0) - 1`), and mapped batches stream directly into Pebble inverted chunk records (`'c'`). Meanwhile, an asynchronous `TileReaper` prunes local cache files behind `SafeWatermark = min(m_kv_size, MPT.PersistedVersion())`.

### Architectural Highlights

- **Direct Inverted Chunk Commits**: Eliminates the intermediate Pebble WAL (`'w'`), streaming mapped key associations directly into inverted index chunk records (`'c'`).
- **Managed Tile Caching**: Raw entry bundles are pre-cached in `ManagedTileCache` on local storage or memory.
- **Dynamic Safe Watermark Pruning**: `TileReaper` actively purges cached tiles behind `SafeWatermark = min(m_kv_size, MPT.PersistedVersion())`, maintaining a strictly bounded disk cache without risking crash-recovery replay durability.
- **Dedicated CPU Isolation**: Worker pool mapping consumes `GOMAXPROCS-1` parallel workers, reserving CPU capacity for Pebble write batches, MPT tree updates, and query serving.

## 7. Concurrency Architecture

The Zero-WAL pipeline utilizes a pipelined concurrency model to balance CPU-bound mapping against I/O-bound database persistence and cryptographic tree hashing.

### Concurrency Pipeline Diagram

```text
[Input Log / ManagedTileCache]
              │
              ▼ (Stage 1: I/O Bound Fetch)
┌─────────────────────────────────────────────────────────────┐
│ TileFetcher & Cache Pool                                    │
│ • Unpacks tiles into contiguous LeafBundles (256 leaves)    │
└──────────────────────────────┬──────────────────────────────┘
                               │ chan *LeafBundle
                               ▼ (Stage 2: CPU Bound Mapping)
┌─────────────────────────────────────────────────────────────┐
│ Mapper Worker Pool (runtime.GOMAXPROCS(0) - 1)              │
│ • 23 parallel workers on 24-core host                       │
│ • Executes MapFn parsing & SHA-256 key hashing              │
│ • Emits unordered MappedBatches                             │
└──────────────────────────────┬──────────────────────────────┘
                               │ chan *MappedBatch (unordered)
                               ▼
┌─────────────────────────────────────────────────────────────┐
│ Resequencer Priority Queue                                  │
│ • Min-heap / ring buffer indexed by BundleIdx               │
│ • Monotonically reorders batches into gapless sequence      │
└──────────────────────────────┬──────────────────────────────┘
                               │ chan *MappedBatch (ordered)
                               ▼ (Stage 3: Database Commit Plane)
┌─────────────────────────────────────────────────────────────┐
│ Pebble KV Committer & MPT Publisher                         │
│ • Direct streaming into inverted chunks ('c')               │
│ • MPT root computation & Tessera Output Log commitment      │
└─────────────────────────────────────────────────────────────┘
```

### Worker Allocation & Reordering Mechanics

- **Mapper Worker Pool**: Defaults to `runtime.GOMAXPROCS(0) - 1` (23 parallel workers on a 24-core host). This dedicates the remaining CPU capacity to Pebble chunk writes, MPT state updates, and live query serving without saturating host CPU cores.
- **Monotonic Resequencing via Priority Queue**: Because variable-length leaves cause parallel map workers to complete bundles out of order, the `Resequencer` buffers completed `MappedBatch` instances in a priority queue min-heap keyed by `BundleIdx`. Batches are released to the Pebble KV committer plane in strictly ascending chronological order before being committed to Pebble.
- **Backpressure Control**: Buffered Go channels connecting pipeline stages enforce backpressure automatically, preventing unbound memory growth when downstream Pebble chunk writes or MPT publishing experience disk I/O pauses.
